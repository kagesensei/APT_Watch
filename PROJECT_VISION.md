## Product vision

APT_Watch should become a local-first, analyst-centered cyber threat intelligence and threat-hunting workbench.

Its purpose is to transform freely available, legally reusable public intelligence into defensible, traceable, actionable assessments of:

- Threat actors and competing vendor names
- Campaigns and operations
- Motivations, capabilities, targeting and victimology
- Tactics, techniques and procedures
- Malware and tools
- Adversary infrastructure and IOCs
- Vulnerabilities and exploitation evidence
- Detections and detection gaps
- Mitigations and defensive priorities
- Hunt hypotheses, evidence, findings and outcomes
- Changes in the threat landscape over time

It must be more than a feed aggregator, ATT&CK browser or generic RAG chatbot. It should implement the intelligence lifecycle and support hypothesis-driven threat hunting.

## Intellectual foundation

Use these principles, derived from my recent study, without copying copyrighted book text:

1. Apply AI only where it adds measurable value. Deterministic parsing, SQL, explicit rules and ordinary statistics should remain deterministic.
2. Follow the intelligence lifecycle:
   - Requirements and prioritization
   - Collection planning and source mapping
   - Processing and normalization
   - Validation and corroboration
   - Analysis using structured methods
   - Production
   - Dissemination tailored to the audience
   - Feedback and continuous improvement
3. Support repeatable, hypothesis-driven hunts:
   - Question or hypothesis
   - Scope and assumptions
   - Required telemetry
   - Relevant intelligence
   - ATT&CK behaviors
   - Search/detection logic
   - Evidence collected
   - Findings and confidence
   - Recommended action
   - Outcome and lessons learned
4. Favor durable adversary behaviors and TTPs over brittle atomic IOCs.
5. Use several analytical lenses appropriately:
   - MITRE ATT&CK for behavior
   - Diamond Model for adversary/capability/infrastructure/victim relationships
   - Kill Chain for attack progression
   - Pyramid of Pain for indicator value
6. Preserve competing hypotheses, contradictory reporting, uncertainty and intelligence gaps.
7. Never convert similarity into attribution without evidence.
8. Keep the analyst in control. AI may assist collection, extraction, correlation, summarization and hypothesis generation, but it must not silently make attribution or operational decisions.
9. Measure usefulness: source freshness, coverage, false positives, corroboration, detection coverage, hunt yield, time saved and analyst feedback.

## Local reasoning model

The chatbot reasoning/synthesis model must be the user's selected abliterated
Meta Llama 3.1 8B Instruct derivative, running locally through
llama.cpp/llama-cpp-python. The user explicitly wants this model so model-level
refusal behavior does not prevent discussion of exploit-related questions.
This intentional choice does not relax evidence-grounded retrieval, citation,
uncertainty, or safety requirements below.

Requirements:

- Record and display the exact derivative identity and provenance. Do not silently substitute a different model.
- Keep APTWATCH_MODEL_PATH configurable.
- Prefer Q4_K_M as the documented laptop-friendly default, but do not hard-code quantization assumptions.
- Display or log the actual loaded model path, model identity, quantization, context size and GPU-layer setting.
- Do not automatically download a model or accept a model license for the user.
- Keep deterministic retrieval separate from LLM reasoning.
- The model may synthesize only the retrieved evidence.
- Require citations and uncertainty language.
- If evidence is insufficient, contradictory or stale, say so explicitly.
- Do not use the model’s pretrained knowledge as an uncited CTI source.
- Fine-tuning may teach response discipline and analytic format, but must not bake volatile CTI facts into the model.
- Evaluate the selected base model before further fine-tuning and retain a reproducible comparison suite.

## Source policy: free does not automatically mean open

Create a machine-readable source registry. For every source record:

- Name and publisher
- Purpose and intelligence level
- Canonical URL
- Retrieval method
- Authentication requirement
- Cost
- License or terms-of-use URL
- Redistribution restrictions
- Rate limits
- Update frequency
- Expected schema/version
- Last successful retrieval
- Last attempted retrieval
- Content hash or upstream version
- Parser version
- Row counts accepted/rejected
- Data-quality result
- Enabled/disabled status

Classify sources separately as:

- Open-source software
- Openly licensed data
- Publicly accessible data
- Free API requiring registration/key
- Free for limited use
- Restricted from redistribution
- Unknown terms—disabled until reviewed

Do not call something “open source” merely because it is free to access. Do not scrape sites whose terms do not permit it. For news and vendor research, prefer RSS/Atom or documented APIs. Store headlines, metadata, short permitted excerpts, hashes and canonical links rather than republishing complete articles.

No paid feed may be required for core operation. Optional sources requiring a free API key must degrade gracefully when unconfigured.

## AI and agent constraints

Do not begin with a swarm of autonomous agents.

First build a deterministic, inspectable orchestration pipeline. Any later agent must have:

- One narrow role
- Allowlisted tools
- Read-only access by default
- Bounded iterations and timeouts
- Structured input/output schema
- Full audit log
- Evidence citations
- Validation before persistence
- Human approval before changing curated identity, attribution or confidence records

Treat retrieved reporting as untrusted input. Defend against prompt injection in ingested articles and feeds. Content from a source must never become an instruction to the model or application.

## ML/statistical capabilities

Do not add ML merely for appearance.

Potential later capabilities include:

- Actor similarity using weighted technique/software/infrastructure overlap
- Behavioral clustering
- Infrastructure overlap detection
- Topic modeling of reports
- Entity and relationship extraction
- Anomaly detection
- Duplicate-report and circular-reporting detection
- Population-level vulnerability prioritization

For every model:

- Define the decision it supports.
- Establish a non-ML baseline.
- Separate training, validation and test data.
- Prevent temporal leakage.
- Track precision, recall, false-positive rate and calibration as appropriate.
- Record model/data versions.
- Make outputs advisory and explainable.
- Allow analyst correction and capture that feedback.
- Never present similarity or clustering as attribution.
